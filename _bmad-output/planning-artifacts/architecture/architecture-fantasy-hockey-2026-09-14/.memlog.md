- (decision) [ADOPTED] Paradigm: layered architecture, one dependency direction. Layers: Presentation (internal/web: HTTP handlers, html/template views, autocomplete JS) -> Feature/domain (internal/auth, internal/predictions, internal/scoring, internal/standings) -> Data access (internal/store, owns all reads/writes to fantasy-hockey.yml). Plus External gateways (internal/mailer: Gmail SMTP, used by auth+predictions) and Orchestration (main.go: wiring only). Adopted verbatim from assets/architecture-requirements.md SS1, including its dependency graph.
- (decision) AD-1 [ADOPTED] Go toolchain and module identity. Rule: Go 1.26.6; module path github.com/sommerfeld-io/fantasy-hockey. Verified against current src/go.mod -- already matches exactly.
- (decision) AD-2 [ADOPTED] main.go is wiring-only. Rule: all application logic lives in internal/ packages; main.go only resolves config, opens the data file, and wires dependencies -- no business logic, no mode dispatch.
- (decision) AD-3 [ADOPTED] Dependency injection via function parameters. Rule: side effects (clock, I/O, network, the data-file path) are injected as function parameters rather than read from global state, so every package stays unit-testable without touching real process state.
- (decision) AD-4 [ADOPTED] GoDog acceptance tests. Rule: acceptance criteria are expressed as Gherkin .feature files under src/acceptance-tests/features/, executed via GoDog, for every feature. Confirmed already in place: src/acceptance-tests/features/configure-port.feature, view-home-page.feature.
- (decision) AD-5 [ADOPTED] Build-gate tooling. Rule: the build pipeline runs golangci-lint, gocyclo (complexity limit 10), go-licenses, and govulncheck as gates; a failing gate blocks the build.
- (decision) AD-6 [ADOPTED] Multi-stage Alpine container image. Rule: the Dockerfile stays a multi-stage build (Go build stage, Alpine runtime stage), running as a non-root user. Dockerfile is a protected file per CLAUDE.md -- any change needs explicit user sign-off.
- (decision) AD-7 [ADOPTED] Taskfile orchestration. Rule: build, lint, test, and run commands are defined as Taskfile tasks; the root taskfile.yml delegates to src/taskfile.yml via the go: namespace. Confirmed already in place.
- (decision) AD-8 [ADOPTED] Layered architecture with fixed dependency direction. Prevents: feature packages depending on internal/web, feature packages depending on each other in ways that bypass internal/store, circular dependencies between layers. Rule: presentation depends on feature/domain packages; feature/domain depends on internal/store; internal/store depends on nothing above it. internal/mailer is depended on only by internal/auth and internal/predictions.
- (decision) AD-9 [ADOPTED] A single YAML file as the sole datastore, no database engine. Prevents: re-introducing a database engine, a schema-migration tool, or a separate datastore container. Rule: all persisted state (season, players, teams, deadlines, predictions, results, award finalists, playoff matchups, login codes) lives in one file, fantasy-hockey.yml. internal/store is the only package that reads or writes it. What the app actually writes: only predictions and login codes, at runtime, in response to a player's own actions -- everything else is human-maintained (see AD-23). Constraint accepted deliberately: exactly one process ever writes the file at a time (see AD-27) -- revisit only if a future version needs more than one writer (see Deferred).
- (decision) AD-10 [ADOPTED] Server-rendered presentation, minimal-dependency stance. Prevents: a JS framework, a separate API+SPA split, a third-party router, an ORM. Rule: internal/web renders HTML server-side with stdlib html/template; routing uses stdlib net/http's ServeMux method+path patterns; the only client-side JS is vanilla JS driving the autocomplete widget.
- (decision) AD-11 [ADOPTED] Stateless signed-cookie sessions. Prevents: a server-side session table/store, any built-in revocation mechanism. Rule: a session is an HMAC-signed cookie carrying the player's identity + issued-at; every authenticated request re-issues the cookie, implementing the 30-minute sliding idle timeout (PRD FR-3); logging out clears/stops re-issuing the cookie (PRD FR-4). No session data is ever written to fantasy-hockey.yml. Matches PRD/UX's session-timeout behavior (redirect to Login-email) and the Login flow (full-screen, pre-shell) exactly.
- (decision) AD-12 [NEEDS RECONCILIATION -- see question] Gmail SMTP for all outbound email. Prevents: adding a transactional-email SaaS dependency or library. Rule as written in source: outbound email (login codes, deadline reminders) sent via stdlib net/smtp to smtp.gmail.com:587 with STARTTLS, wrapped in internal/mailer, called by internal/auth and internal/predictions. CONFLICT: PRD FR-22 (deadline reminders) is now deferred out of MVP -- this AD's 'deadline reminders' half needs updating; login-code sending is unaffected and stays MVP. Also: PRD addendum.md (bmad-prd workspace) specifies local-dev needs a local email-capture server (Mailpit/MailHog-style) in docker-compose with externally-configurable SMTP settings -- this source AD hardcodes smtp.gmail.com, which would NOT let local dev point at a capture server. Needs the user's call -- see question entry.
- (decision) AD-13 [ADOPTED] Gmail App Password as a runtime secret. Prevents: hardcoding the sending account's credentials or assuming plain password auth. Rule: the sending Gmail account has 2-Step Verification enabled and an App Password generated manually, outside the app; the App Password is supplied to the app only as a runtime secret/env var, never committed.
- (decision) AD-14 [ADOPTED] Plain HTTP behind a reverse proxy added later; arm64 target. Prevents: the app terminating TLS itself, or assuming an x86 runtime. Rule: the app serves plain HTTP (no TLS); TLS/exposure is a reverse proxy's job, set up outside this architecture. The Dockerfile targets arm64 (Raspberry Pi deployment).
- (decision) AD-15 [ADOPTED] Leaderboard and scores computed live, never cached or persisted. Prevents: a stored score value that can drift from the underlying predictions/results -- the stale/miscalculated-score failure mode the whole rebuild exists to eliminate. Rule: internal/scoring and internal/standings compute points on every read directly from internal/store's in-memory predictions/results/award-finalist data; no score value is ever written to fantasy-hockey.yml. (Terminology note: PRD/UX renamed 'Standings' to 'Leaderboard' -- package name internal/standings is an internal Go identifier, not user-facing text, so it is unaffected and stays as-is.)
- (decision) AD-16 [ADOPTED] RFC3339 timestamps everywhere. Rule: every date/timestamp (deadlines, issued-at, used-at) is an RFC3339 string, produced via internal/clock.Now(). Confirmed: src/internal/clock/clock.go already exists.
- (decision) AD-17 [ADOPTED] ID strategy: UUIDs only for what the app creates, human-readable keys for everything hand-maintained. Prevents: two builders picking different ID shapes for the same kind of entity; requiring someone hand-editing fantasy-hockey.yml to invent and paste UUIDs for data they're typing themselves. Rule: app-created-at-runtime entities (Prediction, LoginCode) get an application-generated UUID string. Every hand-maintained entity (Player, Team, Deadline, Result, AwardFinalist, playoff matchup) uses a short human-readable string key -- player slug (basti), team abbreviation (TOR), deadline key (preseason), round/series key (round1.s1). Nothing a human types by hand is ever a UUID.
- (decision) AD-18 [ADOPTED] Error wrapping, no custom error envelope. Rule: errors are wrapped with fmt.Errorf("context: %w", err) per Go idiom; no custom error-envelope/response type exists.
- (decision) AD-19 [ADOPTED] Autocomplete data delivered embedded, not via a JSON endpoint. Prevents: a separate JSON API surface being introduced for autocomplete, which would contradict the server-rendered, no-API-split stance (AD-10). Rule: canonical team and NHL Player candidate lists are embedded as JSON directly in the rendered page (server-side, at render time) for the vanilla-JS autocomplete widget to filter client-side -- no dedicated /api/... JSON endpoint anywhere. Every embedding site uses the identical object shape {id, label} and the same shared widget script. (Terminology: 'player candidate list' in the source AD refers to the PRD's NHL Player concept -- the award-finalist autocomplete list -- not the pool's 3 Players; naming clarified in the distilled spine.)
- (decision) AD-20 [ADOPTED] LoginCode is a tracked entity, hashed, never plaintext. Prevents: treating a login code as transient/in-memory state, which cannot satisfy the rule that multiple codes may be simultaneously valid per player, each independently expiring (PRD FR-2). Rule: internal/store persists one login-code entry per issued code (player, code_hash, issued-at, used-at nullable); stored value is sha256(code), never plaintext; validation hashes the submitted code and compares hashes. A code is valid only while unused and within its validity window (10 min, PRD FR-2); requesting a new code adds a new entry rather than mutating/replacing an existing one -- matches PRD FR-1's 'requesting a new code does not invalidate an earlier still-valid one.'
- (decision) AD-21 [ADOPTED] Import-boundary enforcement via golangci-lint depguard. Prevents: the dependency-direction rule (AD-8) existing only as prose that a build can silently violate. Rule: .golangci.yml enables the depguard linter with rules encoding AD-8's forbidden import edges (feature packages never import internal/web); a violation fails task go:lint (AD-5's build gate), not just code review.
- (decision) AD-22 [ADOPTED] Session-signing secret is a required runtime env var. Prevents: an in-process-generated HMAC secret silently invalidating every session (logging every player out) on every container restart. Rule: the HMAC key used to sign session cookies (AD-11) is read from a required SESSION_SECRET env var at startup; the process fails to start if it is unset -- never generated in-process.
- (decision) AD-23 [ADOPTED] Results, deadlines, and playoff matchups are human-maintained; the app only reads them. Prevents: building a management/admin UI or an internal/results-style write path (PRD SS5 Non-Goals is explicit: no admin role/screen of any kind); any feature package assuming it can write a Result, AwardFinalist, Deadline, or playoff matchup entry. Rule: award finalists/winners, team results, series results, playoff matchups, and each prediction set's deadline are all written by a human directly editing fantasy-hockey.yml -- no Go code path ever writes any of them. internal/predictions reads deadlines (lock check, PRD FR-8) and playoff matchups (round-gating, PRD FR-20); internal/scoring and internal/standings read results and award finalists (AD-15). No package exposes a way to create/modify these sections; internal/store's writers cover only predictions and login codes (AD-9).
- (decision) AD-24 [DEFERRED -- was an AD, now moot for v1, see question] Reminder send is synchronous and request-triggered -- no ticker, no dedupe log, as originally specified: clicking 'Send reminder email' calls an internal/web handler that synchronously invokes internal/predictions' completion check and sends via internal/mailer, within the same HTTP request, no goroutine/queue/ticker. CONFLICT: PRD FR-22 (the whole reminder-email feature, including its trigger) is now deferred out of MVP scope entirely (PRD SS6.2, UX EXPERIENCE.md 'Deferred' section) -- there is no trigger surface in v1 at all. This AD's synchronous-not-ticker rule is preserved as guidance for WHEN this gets built later, but is not itself an MVP build decision -- moves to Deferred in the distilled spine, not Invariants & Rules.
- (decision) AD-25 [ADOPTED] Data-file location: env var or CLI flag, flag wins. Prevents: no way to point the same built binary at a different file (dev/test/prod) without rebuilding or editing a committed file. Rule: the path to fantasy-hockey.yml is resolved via a DATA_FILE env var or a --data-file CLI flag (stdlib flag, no third-party CLI/config library); if both set, flag wins. If the resolved path doesn't exist, internal/store creates it (AD-26) rather than refusing to start.
- (decision) AD-26 [ADOPTED] First-run bootstrap creates the data file if it doesn't exist. Prevents: every feature package assuming the file (and a season within it) already exists, with no code path that ever creates it. Rule: on startup, if the file at the resolved path doesn't exist, the app creates it with an initial skeleton: current season + the fixed list of players (name + email). Because there is no registration/admin-invite flow (PRD SS5 Non-Goals), that initial player list must come from somewhere out-of-band before first run -- a hand-authored starter file deployed alongside the app, or a one-time seed value read only when creating a brand-new file. Which mechanism is an implementation choice, not fixed here; once the file exists, it is the only source of truth for who the players are.
- (decision) AD-27 [ADOPTED] Atomic whole-file writes; single-process, single-writer safety. Prevents: a crash or concurrent write leaving fantasy-hockey.yml half-written or corrupted -- this design's equivalent of a database transaction. Rule: internal/store loads the whole file into memory once at startup. Every write updates that in-memory structure under a mutex, then serializes the entire file back to disk by writing to a temporary file in the same directory and renaming it over the original -- never writing in place. A multi-field prediction save updates the in-memory structure once and triggers exactly one write-and-rename. Relies on the app being the only process that ever writes the file at once (AD-9's accepted constraint) -- no locking against a second writer, none expected to exist. This is the same constraint the PRD addendum.md flagged and the user consciously deferred (write-queuing mechanism noted there as a future concern, not built now) -- fully consistent, no conflict.
- (decision) AD-28 [ADOPTED] internal/store owns domain entity structs and shared enums. Prevents: two feature packages independently defining their own Prediction (or other shared entity) Go struct with incompatible shapes, or the same cross-cutting value encoded with different casing/vocabulary in different places. Rule: internal/store exports the canonical Go struct for every entity it owns (store.Prediction, store.Player, store.AwardFinalist, etc.), matching the YAML shape, with yaml struct tags -- feature packages import and use these structs as-is. internal/store also exports typed constants for every cross-cutting enumeration (e.g. Prediction.Kind, AwardFinalist.Award) -- no feature package re-derives its own string literal for a value it doesn't own.
- (constraint) Consistency conventions [ADOPTED from source]: Naming -- package names short/lowercase/singular/no underscores (auth, predictions, scoring, standings, mailer, store, web, clock), no generic names (util, common). Data & formats -- IDs per AD-17, shared structs/enums per AD-28, RFC3339 dates per AD-16, error wrapping per AD-18. State & secrets -- session per AD-11/AD-22, data-file location per AD-25/AD-26, SMTP_USERNAME/SMTP_APP_PASSWORD env-only (AD-13), no in-app alerting (failures surfaced only via externally exported logs, never in-app UI).
