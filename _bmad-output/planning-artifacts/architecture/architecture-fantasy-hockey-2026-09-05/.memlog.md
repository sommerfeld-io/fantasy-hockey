- (decision) Process topology: ONE Go binary with mode selection (e.g. 'serve' vs 'sync' subcommand/arg), not two separate binaries. Single Docker image; docker-compose runs the same image as different services by varying the command. Reason: avoids publishing/maintaining 2 images for a 3-person hobby app; mode dispatch gives full control from one artifact.
- (constraint) [ADOPTED] Brownfield conventions ratified from existing src/ code: Go 1.26.4, module github.com/sommerfeld-io/fantasy-hockey; all application logic lives in internal/ packages, main.go only wires; dependency-injected functions for testability (func params for side effects like clock/io); GoDog BDD acceptance tests in acceptance-tests/; golangci-lint + gocyclo(10) + go-licenses + govulncheck as build gates; multi-stage Alpine Dockerfile (golang:1.26.4-alpine3.24 build -> alpine:3.24.0 runtime, non-root user); Taskfile orchestration.
- (decision) Design paradigm: Layered Architecture. Presentation (internal/web: HTTP handlers/templates) -> feature/domain packages (internal/auth, internal/predictions, internal/scoring, internal/standings, internal/awards, internal/sync) -> shared data-access layer (internal/store, owns all reads/writes for Participants/Seasons/Teams/Predictions/Results). Dependency direction: presentation depends on feature packages depends on store; store depends on nothing above it; feature packages must not depend on internal/web.
- (decision) Storage: PostgreSQL, own container. Reason: web and sync run as separate containers per the one-binary-multi-mode topology and both read/write the same data concurrently -- SQLite's single-writer file-locking across containers is the exact scenario to avoid.
- (version) PostgreSQL 18 (current stable 18.6 as of Aug 2026, verified via web search) -- Docker image tag family postgres:18-alpine
- (version) Go Postgres driver: jackc/pgx v5 (v5.10.0 current, verified via web search) -- supports Go 1.25+ and Postgres 14+, fits existing Go 1.26.4
- (decision) Presentation layer: Option A, server-rendered Go. html/template (stdlib, no extra dep) for templates, stdlib net/http ServeMux (method+path patterns, native since Go 1.22) for routing. Vanilla JS only for the autocomplete widget interaction. No JS framework, no separate API+SPA split, no third-party router, no ORM -- consistent minimal-dependency stance throughout.
- (decision) Session storage: stateless, HMAC-signed cookie (participant + issued-at embedded, re-issued each authenticated request to implement the 30-min sliding idle timeout). No server-side session table -- no revocation requirement exists in the PRD/threat model.
- (decision) Email delivery: Gmail SMTP (smtp.gmail.com:587, STARTTLS) via stdlib net/smtp, no extra dependency. Used for login codes (FR-1) and deadline reminders (FR-10).
- (version) Gmail SMTP requires an App Password (2-Step Verification must be enabled on the sending Google account) as of 2026 -- verified via web search. Rate limit ~500 recipients/day consumer Gmail, far above this app's volume (3 participants).
- (constraint) Operational prerequisite (not automatable by the architecture): the Gmail account used for sending must have 2-Step Verification enabled and an App Password generated manually; the App Password is supplied to the app as a runtime secret/env var.
- (decision) Deployment: plain HTTP only, no TLS in the app itself -- a reverse proxy (to be set up later, outside this architecture's scope) handles exposure/TLS. Target host: Raspberry Pi (arm64) -- already covered by the existing multi-arch Dockerfile.
- (decision) Scoring Engine computes standings/points live on every read from Predictions+Results in Postgres -- nothing cached or persisted as a stored score. Reason: trivial data volume (3 participants) makes on-the-fly computation cheap, and it eliminates stale-cache bugs entirely.
- (decision) Sync implementation (default, not separately elicited): a time.Ticker loop inside 'sync' mode -- runs once on startup then on the configured interval (FR-14). NHL API calls live in internal/nhlclient, using stdlib net/http, implementing the write-nothing-on-failure-or-schema-mismatch rule (FR-16) before touching internal/store.
- (decision) Data conventions: dates/timestamps as RFC3339 strings (matches existing internal/clock.Now() convention already in the codebase); internal entities (Participant, Season, Prediction) use Postgres native uuid as primary key; Team uses the NHL API's own team identifier as its stable technical ID (not a locally generated UUID), since the whole point of FR-15 is stability tied to the real-world NHL entity; errors wrapped with fmt.Errorf(%w) per Go idiom, no custom error-envelope type.
