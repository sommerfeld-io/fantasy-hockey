**Edge-Case Hunter** (complete — all three findings independently re-verified against the real code before being recorded here, per this skill's own re-check rule):

- **Confirmed real, high severity — a duplicate key inside `results:` silently zeroes unrelated, well-formed sibling fields, not just the duplicated one.** `loadExisting`'s doc comment (`store.go:402-407`) claims a tolerated shape error leaves "every field the type mismatch didn't touch, including sibling fields in the same struct... exactly as if this error never happened." **I reproduced this directly against the real `go.yaml.in/yaml/v3` library and then through the actual `store.New` production path** (throwaway probe, `/tmp/yaml-verify/main.go` and a temporary `store` package test): an ordinary single-field type mismatch (e.g. `playoffs: FLA`) does leave siblings intact exactly as claimed — but a **duplicate key** at the same struct level (e.g. `results:` containing `team_marks:` twice) does not: `PresidentsTrophyWinner()` and `StanleyCupWinner()` both come back empty after `store.New` succeeds, even though both were correctly hand-typed as `FLA` in the fixture and are completely unrelated to the duplicated `team_marks` key. `ResultProblems()` reports exactly one message (naming only the duplicate `team_marks` key), giving no hint that `presidents_trophy`/`stanley_cup_winner` were also silently wiped in memory. **Consequence**: for the life of the process, the Leaderboard would score every player's Presidents' Trophy and Stanley Cup picks as unset/0, even though they were correctly recorded and the file itself is never touched (the raw-node splice means the on-disk bytes are untouched — this is a live, in-memory scoring bug, not data loss on disk). A duplicate key is a plausible hand-edit mistake (e.g. pasting a block twice while editing). This is narrower than AC2's own promise ("does not wipe or rewrite what the human wrote in that section") — the promise is broken for well-formed *siblings* of a malformed entry, not just the malformed entry itself, and no story-level review caught it because none tested a duplicate-key fixture. **Disposition: needs a human decision** (routed to Action items and Open questions, not silently fixed) — go.yaml.in/yaml/v3's duplicate-key handling appears to abandon populating the rest of that struct level, which may not be straightforward to isolate without decoding `results:`'s sub-sections independently.
- **Checked, confirmed real, but matches the frozen spec exactly — not a defect.** `SaveDivisionPicks`/`SaveAwardPicks` call `writeLocked` unconditionally even when the picks map produces zero upserts (e.g. an all-blank divisions/awards form submission, reachable for real from `handleDivisionsSubmit`/`handleAwardsSubmit` — confirmed no upstream guard rejects an all-blank submission). This does perform a real disk write-and-rename and does emit a `store write` log line for a functionally no-op submission, which the broader "a no-op call still stays silent" framing (from 7.1's own commit message) doesn't fully capture. But spec-7-1's own I/O & Edge-Case Matrix scopes "no-op" narrowly to exactly two cases — an unmatched login-code request and an unmatched code-consumption attempt, both of which never reach `writeLocked` at all — and explicitly lists `SaveDivisionPicks`/`SaveAwardPicks` under "Successful mutating call: exactly one info line" whenever called and it succeeds, with no upsert-count carve-out. The code matches this frozen spec precisely. **Disposition: accept as-is** — the only "fix" would be to the commit message's broader framing, which is prose, not code; hobby-scale threat model makes the wasted I/O immaterial.
- **Real, cheap, worth fixing.** No doc comment states that `writeLocked` (post-7.4) only ever persists `s.doc.LoginCodes`/`s.doc.Predictions` — the other 8 document fields (`Season`, `Players`, `PredictionSets`, `Teams`, `NHLPlayers`, `PlayoffMatchups`, `Results`, `AwardFinalists`) are never read from `s.doc` again; they're persisted straight from `s.raw`'s untouched nodes. Before this diff, `writeLocked` persisted whatever was currently in `s.doc` wholesale. **Consequence**: a future method that mutates one of those 8 fields in memory, expecting the old "whatever's in `s.doc` gets written" contract, would have that change silently never reach disk — no error, no log line. **Disposition: fix now** (cheap — one doc comment on `writeLocked` or the `document` type stating this boundary explicitly).
