### Direct findings (this retro, verified against the current code)

- **Confirmed real, and worse than it first looks — the "no links inside game-rules.md" convention (AC2) has zero automated enforcement, and the rendering pipeline actively invites the violation.** `TestRulesHTMLShouldNotContainRawMarkdownSyntax` (`internal/web/rules_test.go:16-22`) only asserts the absence of raw, unrendered markdown syntax (`"## "`, `"**"`) — it never checks the rendered HTML for `<a href=` tags, and no other test or lint rule checks `game-rules.md`'s source for `[...](...)`-style links either. **Independently confirmed at the library level and empirically** (edge-case-hunter lens + my own re-verification): `rules.go:16`'s `goldmark.New(goldmark.WithExtensions(extension.GFM))` bundles `extension.Linkify` (`GFM.Extend` calls `Linkify.Extend(m)` directly, `goldmark@v1.8.6/extension/gfm.go`) — GFM's auto-linkify feature. A throwaway render confirmed a bare `https://example.com` or a bare `pool@example.com` in the source markdown auto-converts to a real `<a href=...>`/`mailto:` link with **no markdown link syntax at all** — a plain relative reference like `docs/foo.md` does not, but any URL or email mentioned in passing prose does. The convention holds today only because I checked the current content by hand (see Behavior verification), not because anything guards it. **Disposition: fix now** — cheap, add a `strings.Contains(string(rulesHTML), "<a ")` assertion to `rules_test.go`; consider also whether `Linkify` is wanted at all given the epic's own explicit no-links design intent (`goldmark.WithExtensions(extension.Table, extension.Strikethrough, extension.TaskList)` would keep GFM's other features without auto-linking).
- **Confirmed real — the app-shell's cross-destination identity-regression scenario doesn't cover the new Rules tab.** `app-shell.feature`'s "Navigating between destinations keeps showing the player's identity" scenario (added originally per Epic 1 retro item 2, "extend... to cover /predict, /leaderboard, /compare, not just /") visits Predict, Leaderboard and Compare, but not Rules — even though Rules is a 4th destination added in this very epic, following the exact pattern that motivated the original extension. Verified in code that `handleShell` sets `PlayerName` unconditionally before any tab-specific branch, so this is a coverage gap, not a live defect — Rules does show the player's name today. But it's exactly the class of gap this repo has hit and fixed before (Epic 1 retro item 2), and the individual "shows Rules content" scenario was added correctly while this cross-cutting one was missed. **Disposition: fix now** — cheap, one more `And the player visits the Rules destination` step in the existing scenario.

### bmad-review (Adversarial, Edge-Case Hunter, Verification Gap lenses, full epic diff `5f45fab..0b31f45`)

**Verification Gap** (complete — both findings independently re-verified against the real repo before being recorded):

- **Confirmed real, significant — the "docs and README/embedded-rules never drift" claim has no working enforcement anywhere, and this repo's own agent-facing verification workflow can't catch it either.** Independently re-verified every part: `.github/workflows/pipeline.yml`'s push/pull_request triggers both carry `paths-ignore: ['**.md', 'docs/**', ...]` (confirmed) — a commit touching only `docs/game-rules.md` doesn't trigger the pipeline at all. Even when the pipeline does run, its `lint` job (matrix over `['yaml','workflows','filenames','folders','gherkin','markdown-links']`) calls `docker compose up lint-$LINTER --exit-code-from lint-$LINTER` directly — never the root `task lint`, which is the only place `docs:readme`/`docs:embed-game-rules` are wired in. `common:copy` (`.task/common/taskfile.yml:15-22`, backing both sync tasks) is a bare `cp "{{.SRC}}" "{{.DEST}}"` — an unconditional overwrite with no diff/drift check, so even a local `task lint` run silently regenerates the files rather than failing loudly on drift. And critically: `src/taskfile.yml`'s `build`/`run` tasks (backing `task go:build`/`task go:run` — the exact two commands this repo's own `CLAUDE.md` "Verification Workflow" section instructs an agent to run after every change) call a *same-file* `lint` task scoped to Go-only linters, never the root-level `docs:readme`/`docs:embed-game-rules` tasks. Only `task lint` or `task docker:build`, run manually from the repo root, would ever regenerate (silently) or expose the drift. Independently corroborated by the edge-case-hunter lens, arriving at the same conclusion from the "claims" angle. **Consequence**: a docs-only change to `docs/game-rules.md` (exactly the scenario Story 8.2's own AC describes) can be committed with the embedded copy left stale, the binary still serves the old rules text, CI stays green, and — per the path-ignore — the pipeline may not even run. **Disposition: needs a human decision** on how much to invest — a lightweight `go test` byte-comparison between `docs/game-rules.md` and the embedded copy would close this cheaply and *would* run under `task go:test`/CI's `sonar-analysis` job and under this repo's own agent workflow, unlike a CI-pipeline-level fix, which would mean editing `.github/workflows/pipeline.yml`, a protected file requiring the user's explicit ask.
- Investigated, not a finding: whether a goldmark rendering failure or a missing embed could reach `mustRenderGameRules`'s panic branches untested. Confirmed both `panic` branches are effectively unreachable in normal operation (a missing `//go:embed` target fails at compile time, before the panic path could ever run; `goldmark.Convert`'s only failure mode is a `Write` error from a `*bytes.Buffer`, which never returns one) — the code comment's "fails fast on a broken embed" framing is imprecise but not a live risk. The tab-mutual-exclusivity question (does any test prove `/rules` doesn't also render Predict/Leaderboard/Compare markup) was checked and found to have no realistic unverified regression path given the pointer/string-emptiness typing and one-tab-per-route invariant — recorded as checked-clean.

**Edge-Case Hunter** (complete — the Linkify finding above is this lens's; two more, both re-verified):

- **Confirmed real, low-likelihood — an emptied or whitespace-only `game-rules.md` renders a blank Rules tab with the nav still showing it active, and no error anywhere.** Verified empirically: rendering whitespace-only markdown through the exact `goldmark.New(goldmark.WithExtensions(extension.GFM))` configuration `rules.go` uses returns `err=nil, output=""`. Since `shellData.Rules` is `template.HTML` (empty-string falsy) and `templates/shell.html`'s tab chain is `{{if .Predict}}...{{else if .Rules}}{{end}}` with **no final bare `{{else}}`**, an empty `rulesHTML` on the Rules tab means none of the four branches match — the `<main class="shell-content">` region renders completely empty, silently, for the app's entire uptime (computed once at package init). Low likelihood — `game-rules.md` is a repo-committed, PR-reviewed file, not user input — but cheap to close and consistent with `mustRenderGameRules`'s existing "fail fast on a programmer error" philosophy for its other two branches. **Disposition: defer** — add a check that panics (matching the function's existing convention) when the rendered output is empty/whitespace-only after trimming.
