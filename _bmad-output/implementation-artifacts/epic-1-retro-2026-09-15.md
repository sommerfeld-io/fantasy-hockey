## Findings

Each story's own review (recorded in its spec's Review Triage Log) already triaged a large number of per-story findings into patch/rejected/false/defer — those are not repeated here except where this epic-level pass changes their disposition. What follows is what only became visible across the whole epic: two independent review lenses (adversarial, verification-gap) plus an aggregate-views pass, run against the full 11-commit diff.

### New, epic-level findings

1. **No test drives a real login-code submission's session cookie through a protected route.** (Verification-gap lens) `TestPostLoginCodeShouldRedirectAndSetASessionCookieOnAValidCode` (`src/internal/web/web_test.go:612-644`) and the acceptance step `aSessionCookieIsSet` (`src/acceptance-tests/enter_login_code_steps_test.go:489-505`) only assert the cookie's `Name`/`HttpOnly`/`Secure` attributes, never that it decodes to the *correct* player id. Every other test that round-trips a session cookie (`web_test.go:368`, `stay_logged_in_steps_test.go:134`, `auth/session_test.go`) constructs its own cookie via `auth.IssueSessionCookie` directly rather than driving it through `handleLoginCodeSubmit`. A wiring regression that passed the wrong/blank player id into `auth.IssueSessionCookie` at web.go:270 would pass every existing assertion. Confirmed: `handleLoginCodeSubmit` sits at 63.2%/78.9% coverage in the two most recent coverage runs, consistent with this gap. **Disposition: fix now** (add a regression test asserting `auth.ParseSessionCookie` on the post-code-entry cookie returns the expected player id, ideally by chaining into a protected-route request as the acceptance suite already does for logout). **Upstream lesson:** cross-story handoffs (a cookie produced by one story, consumed by a later one) need at least one test that exercises the full chain, not just each side independently.

2. **`GET /login` never checks for an existing valid session.** (Adversarial lens, confirmed against `src/internal/web/web.go:209` `handleLoginForm`, which is unconditionally public.) A still-logged-in player who navigates back to `/login` sees the anonymous form instead of being routed into the shell. Neither the login story (1.1, assumes an unauthenticated visitor) nor the app-shell story (1.5, assumes arrival post-auth) owns this seam. **Disposition: fix now** (small — check `auth.ValidateSession` in `handleLoginForm` and redirect to `/` when valid).

3. **`stay-logged-in.feature` and `log-out.feature` only exercise `GET /`, never the three shell routes Story 1.5 added.** (Adversarial lens, confirmed: `thePlayerRequestsAProtectedRoute` in `stay_logged_in_steps_test.go` and `thePlayerMakesTheirNextRequestToAProtectedRoute` in `log_out_steps_test.go` are both hardcoded to `"/"`.) Only `internal/web/web_test.go`'s Go unit tests cover `/predict`, `/leaderboard`, `/compare` for these two behaviors. Per this repo's own CLAUDE.md ("acceptance tests describe observable, user-facing behavior... complement, not replace unit-level TDD"), the BDD layer currently understates the real protected surface. **Disposition: fix now** (parameterize both scenarios/step defs over all four shell destinations, mirroring `app-shell.feature`'s own coverage pattern).

4. **The dual-mux route registration pattern is still unresolved and getting more exposed.** Already flagged and deliberately deferred in commit `d9bf930` (Story 1.5's own review, as "pre-existing pattern, not this story's defect"). Confirmed still present at `src/internal/web/web.go:119-138`: all 4 shell routes are listed once on `authMux` and again on the outer `mux`, with nothing enforcing the two lists stay in sync. Re-surfaced independently by the adversarial lens at the epic level. **Disposition: fix now, elevated priority** — this was reasonably deferred story-by-story, but every remaining epic (2, 4, 5) will add more authenticated routes on top of it, so the drift risk compounds each time. Worth resolving before Epic 2 rather than deferring again. **Upstream lesson:** a "pre-existing pattern, not my defect" disposition is correct for a single story, but an epic retro is exactly the checkpoint where compounding pre-existing risk should get re-weighed instead of re-deferred by default.

5. **HMAC session-cookie test-signing/tampering logic is independently reimplemented in 3 separate Go packages.** (Aggregate duplication-map view.) `internal/auth/session_test.go:21-25` (`signPayload`), `internal/web/web_test.go:39-41` (`signedSessionCookie`), and `acceptance-tests/suite_test.go:93-105` (`signedSessionCookieForTest` + `tamperSessionCookie`) each reimplement the same crypto shape. Each story's own review rejected consolidating its own instance individually ("~10 lines, not worth a cross-package test-support package") — reasonable in isolation, but the wire format has already changed once (Story 1.2's base64url fix) and had to be updated in all 3 places by hand. **Disposition: fix now, low priority** (a small shared test-support package, or accept the status quo explicitly if the churn isn't worth it — this is close enough to call either way, flagged for the human to decide rather than assumed).

### Findings re-confirmed as already correctly dispositioned (no new action needed)

These were independently re-surfaced by the epic-level lenses but were already found, reasoned about, and dispositioned at the story level; re-checked here against the primary source and left as-is:

- Residual timing side-channel in `RequestLoginCode`'s synchronous store write (`auth.go:47-50`) — already recorded in `deferred-work.md` (Story 1.1), accepted for the hobby-scale (3-person) threat model.
- The async `send` goroutine (`auth.go:54-58`) has no shutdown coordination with `main.go`'s graceful shutdown — already recorded in `deferred-work.md` (Story 1.1), accepted as self-healing via retry.
- No rate limiting on `POST /login` or `POST /login/code` — already rejected in Stories 1.1 and 1.2's Review Triage Logs, citing AD-14 (app not yet reachable from the public internet).
- Unbounded `LoginCode` row growth in `fantasy-hockey.yml` — already refuted in Stories 1.1 and 1.2, citing AD-30 (one data file per season, rotated).
- Two players' codes rarely hash-colliding — already rejected in Story 1.2 as astronomically unlikely at 3-player scale.
- A removed/stale player keeps a valid session until idle-timeout — already refuted in Story 1.3, citing AD-11's explicit "no built-in revocation mechanism" trade-off; the same reasoning covers Story 1.5's `handleShell` degrade-not-invalidate behavior for a stale player id.
- No `Secure` cookie attribute — AD-11's own text already scopes this explicitly to land with AD-14's future reverse-proxy work, not a gap this epic owns.

### Open questions (no action item without a human decision)

- **No absolute session lifetime.** The only expiry is the 30-minute sliding idle timeout; there's no cap on total session age. AD-11 documents "no revocation" as an accepted trade-off but doesn't address an absolute maximum. Worth an explicit architecture decision before Epic 2 broadens the authenticated surface further, one way or the other.
- **Post-login redirect drops the originally-requested destination.** A deep link to `/leaderboard` while logged out (or idle-timed-out) currently lands the player on `/predict` after re-authenticating, since `requireSession`'s redirect to `/login` and `handleLoginCodeSubmit`'s redirect to `/` are both unconditional. Neither the PRD nor the UX docs specify whether this matters; needs a product decision, not an assumed fix.

### Process lesson (no ticket, watch going forward)

- `internal/web/web.go` is the epic's top-churn file (293 lines, 10 functions: routing, middleware, 5 handlers, and template rendering all in one file) with no sub-file split established. Not a god-file yet, but every remaining epic adds more routes/handlers to this same package. Worth watching — and worth deciding on a split (e.g. routing vs. handlers vs. rendering) before, not after, it becomes unwieldy.
- Minor, cosmetic: `internal/store/store.go`'s `writeLocked` (added in a later patch round) drops the `"store:"` error-wrap prefix used by the file's earlier methods (`"marshal: %w"` vs. `"store: bootstrap %s: %w"`). Still NFR-6 compliant; take-it-or-leave-it normalization.
