## Findings

Consolidated across: aggregate-view analysis (god-class/size growth, duplication map, pattern divergence), a full spec-to-implementation reconciliation for Stories 2.1–2.3 (2.4–2.6 already carry their own Review Triage Logs from this session's own build/review work, so they weren't re-litigated), and a `bmad-review` diff-scope pass (Adversarial, Edge-Case Hunter, Verification Gap) over Stories 2.1–2.3's combined diff, weighting the boundaries between all three. Every finding below was either verified directly against the current code by me, or is a well-corroborated, precisely-sourced sub-agent report I judged consistent with what I verified elsewhere. Findings already adjudicated in a story's own Review Triage Log are noted as such, not re-routed.

**F1 — [real, high, defer-to-Epic-3] `Upcoming` is enforced only at the Predict-list rendering layer, never server-side.** `handleSheet`/`handleSheetSubmit` (`src/internal/web/web.go:1132-1152,1204-1228`) never check `set.Upcoming` — only `pickableSheetKinds`, existence, and the deadline. Verified directly: a pickable-kind set marked `upcoming: true` typically has a far-future deadline, so `handleSheetSubmit`'s `!deadline.After(now)` check never fires either — the set can be opened *and submitted* via direct navigation, completely bypassing the "dimmed, locked, non-tappable" contract the list page (`Actionable = !set.Upcoming`) enforces only at the link-rendering level. Independently found by both the Adversarial and Edge-Case Hunter lenses. Not reachable today — every one of Epic 2's own pickable sets (cup/presidents/divisions/awards) ships `upcoming: false` — but this is exactly the gate Epic 3's Story 3.2 ("round unlocking based on recorded matchups") will need, and there is currently nothing to build on. **Disposition:** defer to Epic 3, as a load-bearing action item, not a vague TODO — Story 3.2 must either add the missing check or explicitly design a different unlock mechanism and document why `Upcoming` isn't reused. **Process lesson:** no story asked "what happens once a *later* epic's data reaches the branch this flag never exercises itself?" — worth a spec-review checklist item for any flag a story introduces but doesn't fully exercise.

**F2 — [real, medium, defer] Four independent "is this id in the canonical list" helpers, no shared shape.** `isKnownTeamID` (loop-return-bool), `divisionRoster`/`allBelongToRoster` (build-set-then-check), `nhlPlayerBySlug`/`isValidAwardFinalist` (loop-return-struct) — one per sheet kind, same concept, three different shapes. Not a bug; a growing maintenance cost that Epic 3's own new pickable kinds (playoff picks) would keep repeating. **Disposition:** defer — propose a shared roster-membership helper when Epic 3 adds its own sheet kind(s).

**F3 — [real, medium, defer] God-class growth: `web.go` and `web_test.go` grew far past what any single commit's diff would show.** Verified via `git show 5d3254a^:...`: `web.go` grew 315→1698 lines (5.4x), `web_test.go` grew 767→2949 lines (3.8x) across the epic's 6 stories — invisible per-commit (each story added a few hundred lines that looked reasonable alone). `web.go` now mixes routing plus 4 distinct sheet-kind view-model families and their validation/rendering logic in one file, with no same-package file-splitting used. `store.go`/`store_test.go` grew less dramatically (228→675, and to 1499) and with more uniform per-Kind structure — less concerning. **Disposition:** defer — propose splitting `web.go` along sheet-kind boundaries (e.g. `sheet_divisions.go`, `sheet_awards.go`) before Epic 3 adds 3 more pickable kinds on top of the same file.

**F4 — [real, low, fix-now] Three stale/self-contradicting doc comments, two not yet caught.** (a) `newTeamOptions`'s comment (`web.go`) says team-embedding is reserved for "2.3/2.4," but 2.3 uses native `<option>`s instead (per its own Boundaries) and the shape is only ever consumed by awards (2.6). (b) `load_canonical_team_list_steps_test.go`'s comment claims "no UI reads `Store.Teams()` yet," contradicted by 2.3's own `groupTeamsByDivision(st.Teams())` landing in the very same diff. (Item (c), `newAwardFinalistOptions`'s equivalent stale comment, was already caught and fixed in this session's own separate ad hoc code review of Story 2.5/2.6 — see `spec-2-6`'s Review Findings — not counted again here.) **Disposition:** fix now — trivial comment corrections, no behavior change.

**F5 — [real, low, fix-now] Duplicated acceptance-test helper.** `setRowFragment` is copy-pasted verbatim (including its comment) into both `browse_prediction_sets_steps_test.go` and `cup_and_presidents_picks_steps_test.go`. **Disposition:** fix now — hoist into one shared acceptance-test helper.

**F6 — [real, low, fix-now] Inconsistent case-sensitivity between two near-identical fixture-guard steps added in the same diff.** `theFixturePlayerIs` case-folds the player name; its sibling `theSeededPlayerHasAValidSession` (added alongside it) does an exact-case comparison. **Disposition:** fix now — standardize on exact-case (matches how `Player.Name` is compared elsewhere).

**F7 — [real, low, fix-now] `app-shell.feature` regression: the "Predict destination" scenario lost its content assertion.** Verified directly: the "root path aliases to Predict" scenario asserts `And the shell shows the Predict content`; the sibling "The Predict destination shows the shell with Predict active" scenario (which predates it) never got the same line added. Visiting `/predict` directly is checked for chrome (name/season/active-tab) but never its actual content. **Disposition:** fix now — one-line addition.

**F8 — [real, low, fix-now] A test assertion is satisfied by an unrelated substring, not what it claims to check.** `TestPredictShouldShowAClosedPillAndCountdownForASetPastItsDeadline`'s second assertion checks the literal substring `"closed"`, which is already present in the just-asserted `status-pill--closed` CSS class — so it can never actually catch a broken countdown string. **Disposition:** fix now — scope the assertion to the countdown span specifically (mirroring the existing "today"/"tomorrow" tests' pattern).

**F9 — [real, low, fix-now] Missing regression test for an already-deliberate design choice.** No test locks in the "Closed status pill + Submitted (green) accent border" combination for a set that's both past-deadline and previously submitted. Verified the behavior itself is intentional, not a bug: `newPredictSetView`'s `accentCSS` switch (`web.go:152-159`) checks `Upcoming` then `submitted`, never `Closed` — and this was already investigated and explicitly accepted in Story 2.3's own Review Triage Log, matching the authoritative UX reference (`App.jsx`'s `SetRow` accent computation, which also never checks `closed`). **Disposition:** fix now — add the missing test asserting the *current, correct* rendering; do not change the behavior.

**F10 — [real, low, defer] Two related but distinct division-vocabulary risks.** (a) `groupTeamsByDivision` silently drops any team whose `Division` doesn't match one of 4 hardcoded names, with no log — asymmetric with `buildPredictPhases`'s own `slog.Error`-and-skip convention for an unrecognized `Phase`. This exact risk was already raised and low-rejected in Story 2.3's own Review Triage Log on hand-edit-reachability grounds; only the logging-asymmetry is a new angle. (b) The division-name literal (`teamDivisionOrder`) lives in `internal/web` with no single source of truth linking it to `Team.Division`'s own values in `internal/store`. **Disposition:** defer, low priority — (a)'s underlying risk was already accepted; (b) is a real design-ownership question worth raising before Epic 6 ("season rollover") might need to change these names.

**F11 — [real, low, accept-as-is] Speculative infrastructure landed on its second try, not wasted.** `newTeamOptions`/`embedOption` were built by Story 2.2 anticipating Story 2.3 as the consumer; 2.3 didn't use it (native `<option>`s, per its own Boundaries) — but Story 2.6 did, just not the story it was built for. **Disposition:** accept-as-is — mis-predicted which story would need it first, not money wasted.

**F12 — [real, low, defer] Acceptance-test fixture-builder duplication.** `newLoadCanonicalTeamListStore` (2.2) and `newLoadCanonicalNHLPlayerListStore` (2.5) are near-byte-identical; the "lazy fixture + `ensureReady()`" scenario-state pattern is independently reimplemented across 4 step files (2.1, 2.3, 2.4, 2.6). **Disposition:** defer — propose a shared acceptance-test support helper before Epic 3 adds 3 more such files.

**F13 — [already adjudicated, no new action] `SavePrediction` has no concurrency test, unlike `CreateLoginCode`'s.** Re-raised by the adversarial lens working from the diff alone; already explicitly rejected in Story 2.3's own Review Triage Log ("matches the majority existing precedent... `ConsumeLoginCode` also lacks one"). Noted here only to show the retro cross-checked it rather than silently duplicating an already-settled finding.

**F14 — [real, low, defer, bundled] Four hand-edit-reachable-only edge cases, same disposition.** Empty `Store.Teams()` leaves the pick dropdown with no selectable option; a saved pick's team id that's since vanished from `Store.Teams()` renders with nothing visibly selected; no uniqueness guard on duplicate Prediction Set ids; no empty-state message if `PredictionSets()` is ever empty. All four match the same, already-repeatedly-accepted "no validation for hand-maintained data" convention this epic established elsewhere (Stories 2.2–2.6's own Review Triage Logs each independently reached the same conclusion for analogous findings). **Disposition:** defer, low priority — consistent with established precedent, not urgent.

**Confirmed, not a finding — epic-level goal holds end-to-end.** For the three before-season pieces Stories 2.1–2.3 cover (browsing, cup pick, presidents pick), epics.md's own Epic 2 goal ("browse, fill in, submit, edit, and have it all persist and sync across devices") holds structurally: the session cookie carries a stable `PlayerID`, `SavePrediction` keys rows by `(PlayerID, Kind)` in the single mutex-guarded `fantasy-hockey.yml`, so a second device reads the same saved state. No acceptance scenario literally simulates two devices, but no code path would break this either.

**No spec violations found** in Stories 2.1–2.3 against their own frozen ACs (checked directly, not just trusting checkboxes) — see the spec-reconciliation investigation for the full list of what was verified compliant.
