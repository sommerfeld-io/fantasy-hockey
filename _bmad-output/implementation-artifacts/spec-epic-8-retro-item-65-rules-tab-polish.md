## Intent

**Problem:** Three lower-priority gaps around the Rules tab (epic-8 retrospective, item 65): (1) the Rules screen is the only tab with real `h1`/`h2`/`h3` elements, styled ad hoc in `styles.css` with a comment stating "No component spec exists for this in DESIGN.md"; (2) `docs/architecture.md`'s quick-reference table describes `task lint` only as "project-wide linters," with no pointer to the doc/README-regeneration side effect the same document explains two sections later ("Keeping the docs and README in sync"); (3) `.rules table` has no horizontal-overflow handling - `docs/game-rules.md`'s scoring table (3 columns, one with long prose like "5 per name found anywhere in the real top 3 (ties expand the set)") will overflow or cram awkwardly at DESIGN.md's stated mobile-first target width (~360-430px).

**Approach:** Add a Components entry to `DESIGN.md` documenting the Rules screen's actual shipped heading treatment (the values already in `styles.css`), with a cross-reference from the CSS comment back to it. Add a one-clause cross-reference in `architecture.md`'s quick-reference table row for `task lint` pointing at the "Keeping the docs and README in sync" section. Add `display: block; overflow-x: auto` (the standard CSS technique for a scrollable table without a wrapper element) to `.rules table`, verified against the actual wide scoring table at a narrow viewport.

**Review patches:** applied three `patch`-routed blind-hunter findings, one of them a real functional bug in the original fix — the initial `display: block; overflow-x: auto` alone does nothing: with default `table-layout: auto` and no `white-space: nowrap`, the browser just shrinks/wraps long cell text to fit `width: 100%` instead of ever growing wider than it, so there's nothing for `overflow-x: auto` to scroll - exactly the 3-column scoring table the fix was written for would have kept wrapping, not scrolling. Verified real by re-reading the CSS cascade rules (no `nowrap` anywhere on `.rules th`/`.rules td`) rather than assuming the technique alone was sufficient. Fixed: added `white-space: nowrap` to `.rules th`/`.rules td`, and rewrote the CSS comment to state the actual two-part mechanism (nowrap forces natural width, overflow-x scrolls what no longer fits) instead of presenting `display: block + overflow-x: auto` alone as "the standard technique," which was misleading on its own. Also added a "Rules screen tables" bullet to DESIGN.md, closing an asymmetric-documentation gap (finding (1)'s heading treatment got a dedicated bullet, finding (3)'s table-scroll behavior didn't) - corrected an initial draft of that bullet that inaccurately claimed the header row shares the Leaderboard/Compare table's `raised` fill, when `.rules th` actually has no background at all (caught by re-reading the actual CSS before finalizing the doc claim). Three findings dispositioned `low, reject`/`false`: a sticky table header plus a visual scroll-affordance cue (fade/shadow) is a materially larger UX enhancement than "add horizontal-overflow handling" (the item's own wording) calls for; the generic `.rules table` scoping also reaching the narrower 2-column Status/Meaning table is intentional, consistent behavior, not a targeting error - a table that already fits its viewport simply never triggers the scroll container regardless of which rule matches it; and the BDD/acceptance-test policy question doesn't apply the way it would for a testable behavior change - this repo's GoDog acceptance suite runs over `httptest` with no browser/layout engine, so rendered CSS overflow behavior has no mechanism to assert against in this codebase at all, distinct from silently skipping an achievable test.

## Review Triage Log

*(blind-hunter, oneshot route)*

- **medium, patch** — the original fix (`display: block; overflow-x: auto` with no `white-space: nowrap`) doesn't actually trigger horizontal scrolling for the table it was written for: without `nowrap`, `table-layout: auto` just wraps/shrinks long cell text to fit `width: 100%` rather than ever exceeding it, so `overflow-x` has nothing to scroll. Verified real by re-reading the cascade. Fixed: added `white-space: nowrap` to `.rules th`/`.rules td`.
- **low, patch** — the CSS comment presented `display: block + overflow-x: auto` alone as "the standard technique," without noting it only works paired with `nowrap` (or a min-width) - could mislead a future maintainer into thinking the mechanism was already complete. Verified real. Fixed: rewrote the comment to explain the actual two-part mechanism.
- **low, patch** — asymmetric documentation: the heading-treatment gap got a dedicated DESIGN.md Components bullet, but the table-scroll-behavior gap (the exact same class of "shipped-but-undocumented" issue this retro item exists to close) got none. Verified real. Fixed: added a "Rules screen tables" bullet - caught and corrected an inaccurate first draft (claimed a shared `raised` header fill with the Leaderboard/Compare table that `.rules th` doesn't actually have) before finalizing.
- **low, reject** — no sticky table header or visual scroll-affordance cue (fade/shadow) indicating the table scrolls. Not fixed: the retro item's own wording asks for "horizontal-overflow handling," i.e. making the table scrollable at all - a sticky header plus a scroll-cue is a materially larger, separate UX enhancement beyond that scope.
- **low, reject** — the new `.rules table` rule also reaches the narrower 2-column Status/Meaning table, which never had the overflow problem. Not a defect: the scoping is intentionally generic (any `.rules` table gets the same overflow-safe treatment), and a table that already fits its viewport simply never triggers the scroll container - nothing about matching this rule changes its appearance unless it's actually too wide to fit.
- **false** — reviewer flagged that CLAUDE.md's BDD policy requires asking whether an acceptance test applies to this observable rendering change. Not a defect in the sense of a silently-skipped achievable test: this repo's GoDog acceptance suite runs entirely over `httptest`, with no browser or CSS layout engine anywhere in the test stack, so there is no existing mechanism capable of asserting rendered horizontal-overflow behavior at all - the standing policy's premise (a real choice between testing and not) doesn't apply here the way it would for HTML/text-content behavior.
- **false** — spec frontmatter and `sprint-status.yaml` still showed in-progress/open at review time. Not a defect: expected mid-review workflow state, resolved as the final step of this same build.

All three patched findings were independently re-verified after patching: CSS syntax re-checked, the corrected rule re-fetched from a live server run, and the full `task lint`/`gofmt`/`go vet`/`task go:lint`/`task go:test`/`task go:run` pipeline is clean.
