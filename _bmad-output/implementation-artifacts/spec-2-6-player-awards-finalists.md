## Intent

**Problem:** The "awards" Prediction Set still renders Story 2.1's static stub — a player has no way to pick 3 finalists for each of the 5 individual awards (Hart, Norris, Vezina, Art Ross, Rocket Richard), the epic's last before-season prediction, and typo'd free-text names would silently fail to score.

**Approach:** Replace the stub with 5 trophy groups of 3 text inputs each, backed by the app's first true autocomplete widget (`awards.js`): each input pairs a visible text box with a hidden slug field; the widget filters an embedded, position-scoped `{"id","label"}` JSON list (Story 2.5's `Store.NHLPlayersByPosition`, converted via the existing `newAwardFinalistOptions`) as the player types, fills the hidden slug on selection, and clears it (showing a `goal`-colored border) if the text changes without a fresh selection. The server independently re-validates every slug regardless of what the client allowed (AD-10), rejecting the whole submission if any typed-but-unresolved name exists; otherwise it saves every award whose all 3 slots resolved, redirects to `/predict`, and the set shows Submitted once at least one award has a saved pick (mirrors Divisions' own "at least one part saved" convention).

## Boundaries & Constraints

**Always:** Per AD-28, persist one `Prediction` row per award's finalist trio: `Kind = store.KindAward` ("award"), scoped by a new `Award string` field (values `store.AwardHart`="hart", `AwardNorris`="norris", `AwardVezina`="vezina", `AwardArtRoss`="art_ross", `AwardRocketRichard`="rocket_richard" - mirrors `Division`'s own scoping), carrying a new `FinalistSlugs []string` field (length 3, ordered) - row keyed by `(PlayerID, Kind, Award)`, mirroring `Division`-keyed rows exactly. Each award's eligible position is fixed in code (Hart/Art Ross/Rocket Richard → skater, Norris → defenseman, Vezina → goalie) - not hand-maintained data, so no YAML change. Each finalist slot renders as a visible text `<input>` plus a same-named-pattern hidden slug `<input>`; the widget clears the hidden slug on any text change that isn't immediately followed by picking a suggestion, so a stale slug never survives an edited-but-unconfirmed name. Submit is validated as one whole form (mirroring Division picks' own precedent): if any slot has non-blank text but no resolved slug (or - AD-10 - a resolved slug that doesn't actually belong to that award's eligible-position list, re-checked server-side regardless of client state), the entire submission is rejected (200, nothing saved, the offending slot(s) get the `goal`-border + inline caption). Once that gate passes, every award whose 3 slots are all filled (hence all valid) is saved via one batched `SaveAwardPicks` write (mirrors `SaveDivisionPicks`'s snapshot/one-`writeLocked()`/rollback shape); an award left partially or fully blank simply isn't saved this submission (FR-11: scores zero, never blocks another award or another set) - never a validation error on its own. A fully-filled award's group label shows a green check on render, independent of whether the whole set is Submitted. `Store.NHLPlayers()`/`NHLPlayersByPosition` and the existing `newAwardFinalistOptions`/`embedOption` (Story 2.5) are the sole data source and embed shape - no new store accessor beyond `FindAwardFinalists`/`SaveAwardPicks`.

**Never:** No new `/api/...` endpoint - the three position-scoped lists (skaters, defensemen, goalies) embed as JSON directly in the sheet page (AD-19), one script tag per position, reused across every slot needing that position. No client-side validation beyond the widget's own resolved-slug bookkeeping - AD-10 caps this story's JS to exactly the one sanctioned "autocomplete widget" responsibility; the server is the actual enforcement point. No free-text fallback: a name that never resolves to a real NHL Player's slug is never saved, not even as a display string. No change to `Team`/cup/presidents/Division picks' own code paths.

## Design Notes

- Whole-form validation gate (any single typed-but-unresolved name blocks the entire POST, saving nothing) mirrors Division picks' own already-reviewed-and-accepted "Submit is all-or-nothing for the whole form" precedent (spec-2-4) - FR-9's "any subset of a set's fields can be saved independently" is satisfied at the granularity of separate POST requests over time (submit awards today, revise later), not by partially honoring one POST with mixed valid/invalid slots, matching how Division picks' own multi-field form was already interpreted and accepted twice through review.
- An award only ever saves once all 3 of its own slots resolve - a 1-or-2-filled award is treated identically to a fully-blank one (no row, no error), per FR-11 and AD-28's framing of the row as "the trio," not three independent slots.
- The visible-text-plus-hidden-slug pairing is the standard way to satisfy AD-19's "the widget always submits the selected option's id, never label" when the visible control is a free-typed text box rather than a `<select>`/checkbox (which submit their own value directly, as cup/presidents' `<select>` and Division's checkboxes already do) - neither AD-19 nor DESIGN.md/EXPERIENCE.md specify this wiring explicitly, since no earlier story needed a text-typed autocomplete; this is the natural, minimal mechanism that satisfies AD-19's literal requirement.
- `awardEligiblePosition`'s Hart/Norris/Vezina/Art Ross/Rocket Richard → skater/defenseman/goalie mapping is fixed by the PRD/epics.md AC directly (not hand-maintained), so it lives in code as a plain lookup, not YAML - matches how `phaseBeforeSeason`/`phasePlayoffs` and other fixed-by-spec vocabularies are already plain Go consts/maps rather than data.
- The click-dummy `App.jsx`'s own award-finalist state/validation (plain display-name strings, native non-restrictive `<datalist>`, no slug, no rejection, "done" = merely non-empty) is superseded here, not authoritative - PRD FR-17 and this epic's own AC explicitly require stricter, slug-validated behavior the click-dummy never modeled (confirmed by UX docs' own "[ASSUMPTION] Player awards: name rejected" note and the reconcile doc's explicit callout that the click-dummy left this question open).
