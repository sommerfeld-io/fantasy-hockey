## Intent

**Problem:** The "divisions" Prediction Set still renders Story 2.1's static stub ("Not available yet.") — a player has no way to pick playoff teams per division or a division winner, the epic's third before-season prediction (FR-15, FR-16).

**Approach:** Extend the sheet page with a new pick view for `set.ID == "divisions"`: four division groups, each a checkbox-per-team chip list (playoff teams, max 5/division, conferences capped live at 8/8 client-side via a new `divisions.js`, server re-validated) plus one winner `<select>` scoped to that division's own roster. One POST saves everything at once via one new atomic store write. Reuses Story 2.2's `groupTeamsByDivision`/`teamDivisionOrder` for both the chip lists and the winner dropdowns — no new grouping helper.

## Boundaries & Constraints

**Always:** Per AD-28, persist one `Prediction` row per division per pick-type: `Kind = store.KindDivisionPlayoffTeams` ("division_playoff_teams") carrying the new `TeamIDs []string` field, and `Kind = store.KindDivisionWinner` ("division_winner") carrying the existing `TeamID` field — both add a new `Division string` field to `Prediction`, so a row is keyed by (PlayerID, Kind, Division). Submit is all-or-nothing for the whole form: reject with an inline caption, saving nothing, unless both conferences (Eastern = Atlantic+Metropolitan, Western = Central+Pacific — derive each division's conference from its own teams' existing `Team.Conference` field, never a second hardcoded division→conference map) total exactly 8 selected teams each. Winners are never part of that gate (FR-16 has no submit gate) — an empty winner select is accepted and simply never creates/updates that division's winner row (FR-11, no Prediction row force-created for an empty pick); a non-empty winner must belong to that division's own team roster. All 8 possible row upserts for one submission persist through exactly one `writeLocked()` call (epic-2-context.md's "a save triggers exactly one atomic write-and-rename"), rolling back every touched row in memory if that single write fails — mirrors `SavePrediction`'s rollback shape, generalized to a batch. `pickableSheetKinds["divisions"] = true` gates the real form the same way "cup"/"presidents" already do. Client JS (`divisions.js`, the app's first) only disables/dims already-capped sibling checkboxes on `change` (AD-10) — the server re-validates every cap regardless of what the client allowed.

**Never:** No change to `FindPrediction`/`SavePrediction` or the cup/presidents rows (`Division`/`TeamIDs` stay zero-valued/omitted there). No JSON-embedded team data or `teamOption`/`newTeamOptions` for this story — chips are native checkboxes over each division's already server-rendered, small team list, not an autocomplete (that shape stays reserved for 2.6). No partial-form save (no per-division independent POSTs).

## Design Notes

- EXPERIENCE.md's Voice-and-Tone caption ("8 teams per conference — either a 4/4 split, or 5 in one division and 3 in the other.") is authoritative over the click-dummy App.jsx's own placeholder wording, matching Story 2.3's precedent of favoring documented UX artifacts over the click-dummy when they diverge.
- Winner `<select>` options are each division's full static roster (`group.Teams`), never filtered to that player's currently-checked playoff teams — confirmed against the reference `App.jsx` `DivisionForm` winner `Select`, which always renders `DIVISIONS[k].teams` unfiltered.
- `playoffTeamsValid` reference logic: valid ⇔ both conference totals equal 8. **Correction (review loop 1):** the previous version of this note said the per-division 3–5 range is "by construction" and told the implementer not to re-check it server-side — that was wrong. "By construction" only holds for a compliant browser client running the real, unmodified `divisions.js` against the real rendered form; it does not hold for any other client (curl, a disabled-JS browser, a future API caller), and AD-10 requires the server to "independently re-validate and enforce **every** cap on submit regardless of what the client allowed" — plural, not just the conference total. `handleDivisionsSubmit`'s validation chain (`parseDivisionsSubmission`/`divisionConferenceTotals`/`conferenceTotalsValid`, or a new small helper alongside them) must also: (a) reject a submission where any single division's checked-team count exceeds 5, with the same `divisionsCountErrorText` caption used for the conference-total case; (b) de-duplicate a division's submitted team ids before counting or persisting them (a repeated id must count once, not once per repetition). Neither check adds new public surface or a new store method — both belong in the existing private validation helpers, ahead of the conference-total check.
