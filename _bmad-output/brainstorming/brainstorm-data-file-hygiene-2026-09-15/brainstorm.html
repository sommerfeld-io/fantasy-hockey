1ST PERIODGame Film Review — Failure Analysis

Incident Reports from the Penalty Box

Before drawing up any new plays, the coach rewound the tape: real incidents already on record, plus the near-misses a small hand-maintained file is one bad night away from. Fifteen slips filed to the board.

01

Past real incident: the old spreadsheet pool had an uncorrected scoring error nobody could see happen — logging every yaml mutation prevents a repeat by making changes visible as they happen.

02

Runtime yaml corruption risk: yamllint catches bad indentation/line length in CI, but nothing catches it if a runtime write ever produces lint-hostile output — only a runtime check closes that gap.

03

A hand-edit that violates yamllint (tabs, trailing whitespace) can silently persist forever once the app re-writes the file, since nothing validates on load — only the committed baseline in CI.

04

If a future bug in ConsumeLoginCode's expiry check ever misjudges an old row, removing expired rows entirely eliminates the blast radius of that whole bug class instead of just patching the symptom.

05

An active season accumulates many login attempts, making the hand-maintained file diff-noisy over time for the human running the pool — cleanup keeps the file lean and readable.

06

The atomic write-and-rename (AD-27) is solid, but nothing today guards against yaml.Marshal regenerating technically-valid-but-lint-hostile output if a Player field ever contains an unusual string.

07

Without action logging, the human maintainer has no way to answer "did anyone request a code this week" without grepping raw code hashes in the yaml file — stdout logs fill that gap with zero schema change.

08

Real incident from this project's own history: a docker bind-mount root-write left the file root-owned — any future cleanup job must reuse the same writeLocked path so it inherits the same atomic-write safety net.

09

Per FR-2 (Story 1.2), wrong/expired/used codes must render identically to the player — cleanup must preserve that: a deleted expired row must reject a resubmitted code exactly the same as before it was deleted.

10

A cleanup routine running on a hot path (e.g. every FindPlayerByEmail call) risks new lock contention with concurrent RequestLoginCode/ConsumeLoginCode calls on store.mu — needs a deliberate, infrequent trigger point.

11

"Yamllint compliance" at app runtime can't literally mean invoking the yamllint Python tool without a story-level decision — need to scope whether the app enforces a Go-native subset of rules or shells out to the real tool.

12

Retention question: deleting a code the instant it's used destroys any ability to answer "I never got a code" support questions later — used-and-consumed rows may need a different retention rule than expired-and-unused ones.

13

This session's own docker-compose debugging showed how fragile "human reads the file directly" already is — a small, lint-clean file is what makes that hand-editing workflow trustworthy at all.

14

A careless new log line could leak a raw login code or email if it doesn't follow the existing hashCode-never-logged convention — the new logging story needs that same explicit rule stated up front.

15

Cleanup must compare against clock.NowTime(), the same clock already used by ConsumeLoginCode, or tests (and behavior right at the loginCodeValidity boundary) become inconsistent between the two code paths.

2ND PERIODConstraint Mapping

The Boards vs. the Open Ice

Every rink has real boards you cannot skate through, and phantom "rules" players assume are there but aren't. Sorting the two kept the brainstorm from designing around walls that don't exist — and from ignoring the ones that do.

The Boards — real, must respect

  • AD-29: store is the only package allowed to touch the file, single mutex — any new logging/cleanup logic must live inside or be invoked through store.go, never bypass it.
  • "Log to the default output" already means routing through slog.Info the same way the recent auth logging story did — reuse that convention rather than inventing a second logging path.
  • AD-23: the file is hand-edited by a human out of band — automatic cleanup must not silently clobber a concurrent manual edit; atomic write-and-rename handles last-writer-wins but doesn't prevent surprise.
  • loginCodeValidity (10 minutes) is already a named constant in store.go — cleanup's definition of "expired" must reuse that exact constant, never a second, driftable TTL.
  • The actual yamllint ruleset already lives in the repo's .yamllint config — the compliance story should target that same config, not invent a parallel rule set that could disagree with CI.
  • go.yaml.in/yaml/v3's own marshal defaults (indent width, quoting style) may or may not already satisfy .yamllint's config — needs a concrete check before assuming a gap exists at all.
  • CLAUDE.md's BDD rule applies — any of these three stories that changes observable behavior needs Gherkin acceptance coverage unless the human explicitly waives it as infra-only.
  • None of these three stories should need to touch Dockerfile or .github/workflows — a new binary dependency (e.g. real yamllint at runtime) is a flag-for-discussion, not a silent decision.
  • LoginCodes is a single slice in one document struct — removing rows changes indices/length, so any test asserting doc.LoginCodes[i] by position needs re-checking for the cleanup story.
  • Concurrent readers already take s.mu.RLock (FindPlayerByEmail, FindPlayerByID) — a cleanup pass that deletes rows must take the writer lock exactly like CreateLoginCode/ConsumeLoginCode already do.

Open Ice — assumed limits, actually skatable

  • Cleanup does not need a cron/background goroutine just because "cleanup" sounds scheduled — cleanup-on-write or cleanup-on-startup is simpler for a small single-binary pool tool.
  • "Log all actions that change data" doesn't require a new persisted audit trail inside the yaml itself — the simplest real reading is server-side stdout logs only, consistent with what already shipped.
Referee's scope note "Only available codes should remain" likely means unused AND unexpired — i.e. cleanup removes both expired rows and already-used rows, leaving exactly the redeemable set.
3RD PERIODLine Changes — SCAMPER

Substitutions Off the Bench

Seven players, seven letters, sent over the boards one at a time to see what each substitution pattern does to the same three problems.

S
Substitute
  • Instead of a standalone cleanup operation, have ConsumeLoginCode's existing write also prune other expired rows as a side effect of a write that's already happening.
  • Swap plain slog text lines for consistent structured key=value fields (action=, player_id=, rows_removed=) so the new logs stay grep/awk-friendly for whoever runs the pool.
C
Combine
  • Merge the cleanup and logging stories — log a distinct line only when a sweep actually deletes something ("removed 3 expired login codes"), giving free visibility into the new behavior.
  • Merge the yamllint-compliance story into the existing task lint pipeline — an acceptance test that runs the real yamllint binary against a file the app just wrote, instead of reimplementing its rules in Go.
A
Adapt
  • Adapt the atomic write-and-rename pattern to run a cheap self-check post-marshal (e.g. reject/log if the fresh YAML has trailing whitespace) before the rename ever happens.
  • Adapt AD-30's season-suffixed-file convention for a pre-cleanup safety snapshot, instead of inventing a new backup mechanism from scratch.
M
Modify
  • Change CreateLoginCode/ConsumeLoginCode to return how many stale rows they just swept, making cleanup an observable, directly testable side effect rather than an invisible background action.
  • Split retention into two classes — expired-and-unused rows drop immediately, used rows survive a short grace window — rather than one blanket "delete everything not currently valid" rule.
P
Put to Other Use
  • The same "data changed" log line doubles as a lightweight activity signal ("last login was 3 days ago") for the human running the pool, with no dashboard needed.
  • Yamllint-on-load doubles as an early warning for hand-edit typos — the app refusing to boot (or warning loudly) on a lint-violating hand edit catches mistakes before they cause a confusing runtime bug.
E
Eliminate
  • Never persist login codes past use at all.Benched for good reason: breaks FR-2's identical-outcome guarantee and any future ability to investigate a disputed login — recorded as a discarded direction.
  • Skip a runtime yamllint check entirely and trust yaml.Marshal's deterministic output, verifying only at CI time against the committed baseline file — a cheaper variant to weigh against the stricter one.
R
Reverse
  • Instead of cleaning up expired codes after the fact, cap outstanding unused codes per player so a new request invalidates the player's older unused ones — shrinks the cleanup problem at its source.
  • Instead of the app enforcing yamllint on itself, give the human maintainer a task command that lints AND normalizes their hand-edits after the fact, closing the loop from the human side too.

Every coach's whiteboard has a line combo chart. Here, the "positions" are the parameters of each problem — mix and match them, then skate out two full lineups and see how they compare.

ParameterConfigurations mapped
WHENon write / periodic goroutine / on startup / on-demand CLI flag

Logging — WHAT triggers a line × CONTENT

ParameterConfigurations mapped
WHATevery writeLocked call generically / only specific auth actions

Config: row-count deltaInclude a row-count delta in every write's log line ("login_codes: 7 → 4"), generically at the store layer — serves logging and gives cleanup visibility for free.

Yamllint — WHERE × HOW enforced × FAILURE mode

ParameterConfigurations mapped
WHERE / HOW / FAILUREon load / on write / both × shell out to real yamllint / hand-roll rules in Go × reject / log-and-continue
Config: load-onlyYamllint enforced only on load, warning/rejecting a hand-edited file that already violates the rules, trusting the app's own marshal output on write — cheapest variant, still catches human-error typos.

Bundle A — The Safe Line

minimal / low-risk
  • Startup-only cleanup
  • Generic store-level write logging
  • Load-time-only yamllint check

Avoids the hot request path, avoids new CLI surface, avoids a new container dependency.

Bundle B — The Power-Play Unit

maximum visibility / safety
  • On-demand CLI cleanup flag
  • Today's per-auth-action logging, extended
  • Write-time yamllint via the real binary

Most thorough — costs a container dependency and a slightly bigger CLI surface.

FINAL SCORE: 3 STORIES SCOPED

Converging: affinity-clustered into the three requested stories (logging / cleanup / yamllint) plus a cross-cutting constraints cluster, then MoSCoW within each to scope a v1 slice.

League-wide rule — applies to all three stories Explicitly ask the human whether a Gherkin acceptance test is required or can be skipped as infra-only, per this repo's own BDD convention — do not decide silently either way.

Story A — Log Data-Changing Actions

#A
MustOne generic store-level slog.Info line on every writeLocked call, reusing the existing logging convention. Never logging raw codes or emails.
ShouldDistinguish a bootstrap-time write (store.New creating a fresh file) from a normal in-life write in the log line's wording.
CouldInclude a row-count delta per collection (e.g. login_codes: 7 → 4) in the same line.
Won't (this time)A separate persisted audit trail inside the yaml file itself — stdout logging only.

Story B — Cleanup Expired Login Codes

#B
Must
  • "Available" = unused AND unexpired; delete both expired-unused rows and already-used rows, reusing loginCodeValidity and clock.NowTime() as the single source of truth for expiry.
  • Cleanup goes through the existing mutex-guarded writeLocked path — no second write mechanism, no new lock.
ShouldTrigger cleanup opportunistically (on store.New / on the next write) rather than adding a background goroutine or cron.
Could— none raised this round; nothing was benched here, the round simply didn't produce one.
Won't (this time)An on-demand CLI cleanup flag — parked as a fallback if opportunistic cleanup proves insufficient later.

Story C — Yamllint Compliance

#C
MustAn acceptance/integration test runs the real yamllint binary against a file the app just wrote, verified against the repo's existing .yamllint config — not a hand-rolled reimplementation of its rules in Go.
ShouldAlso check on load, warning or rejecting a hand-edited file that already violates the rules, catching human-typo drift before it causes a confusing runtime bug.
Could (flag for human sign-off)Shelling out to the real yamllint binary before every write for the strongest guarantee — this adds a new runtime dependency to the Alpine run-stage image, which touches the protected Dockerfile and needs explicit approval, not a silent default.
Won't (this time)Reimplementing yamllint's ruleset natively in Go.
◤◢ final horn ◣◥
The three stories share one root fix: route cleanup, logging, and lint-verification all through the existing writeLocked path rather than adding parallel mechanisms. Chosen v1 scope — generic store-level write logging (never raw codes/emails), opportunistic cleanup on write reusing loginCodeValidity + clock.NowTime (unused + unexpired = available), and a yamllint-binary-based acceptance test verifying writeLocked output against the repo's own .yamllint config — with a real-binary-on-every-write variant flagged for explicit Dockerfile sign-off rather than decided silently. BDD acceptance-test scoping to be asked of the human per repo convention, for each story.
