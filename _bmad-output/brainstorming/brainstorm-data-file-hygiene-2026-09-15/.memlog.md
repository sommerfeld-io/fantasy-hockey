- (technique) started Failure Analysis
- (idea by coach) Past real incident: the old spreadsheet pool had an uncorrected scoring error nobody could see happen - logging every yaml mutation prevents a repeat by making changes visible as they happen
- (idea by coach) Runtime yaml corruption risk: yamllint catches bad indentation/line length in CI, but nothing catches it if a runtime write ever produces lint-hostile output - only a runtime check closes that gap
- (idea by coach) A hand-edit that violates yamllint (tabs, trailing whitespace) can silently persist forever once the app re-writes the file, since nothing validates on load, only on the committed baseline in CI
- (idea by coach) If a future bug in ConsumeLoginCode's expiry check ever misjudges an old row, removing expired rows entirely eliminates the blast radius of that whole bug class instead of just patching the symptom
- (idea by coach) An active season accumulates many login attempts, making the hand-maintained file diff-noisy over time for the human running the pool - cleanup keeps the file lean and readable
- (idea by coach) The atomic write-and-rename (AD-27) is solid, but nothing today guards against yaml.Marshal regenerating technically-valid-but-lint-hostile output if a Player field ever contains an unusual string
- (idea by coach) Without action logging, the human maintainer has no way to answer "did anyone request a code this week" without grepping raw code hashes in the yaml file - stdout logs fill that gap with zero schema change
- (idea by coach) Real incident from this project's own history: a docker bind-mount root-write left the file root-owned - any future cleanup job must reuse the same writeLocked path so it inherits the same atomic-write safety net
- (idea by coach) Per FR-2 (Story 1.2), wrong/expired/used codes must render identically to the player - cleanup must preserve that: a deleted expired row must reject a resubmitted code exactly the same as before it was deleted
- (idea by coach) A cleanup routine running on a hot path (e.g. every FindPlayerByEmail call) risks new lock contention with concurrent RequestLoginCode/ConsumeLoginCode calls on store.mu - needs a deliberate, infrequent trigger point
- (idea by coach) "Yamllint compliance" at app runtime can't literally mean invoking the yamllint Python tool without a story-level decision - need to scope whether the app enforces a Go-native subset of rules or shells out to the real tool
- (idea by coach) Retention question: deleting a code the instant it's used destroys any ability to answer "I never got a code" support questions later - used-and-consumed rows may need a different retention rule than expired-and-unused ones
- (idea by coach) This session's own docker-compose debugging showed how fragile "human reads the file directly" already is - a small, lint-clean file is what makes that hand-editing workflow trustworthy at all
- (idea by coach) A careless new log line could leak a raw login code or email if it doesn't follow the existing hashCode-never-logged convention - the new logging story needs that same explicit rule stated up front
- (idea by coach) Cleanup must compare against clock.NowTime(), the same clock already used by ConsumeLoginCode, or tests (and behavior right at the loginCodeValidity boundary) become inconsistent between the two code paths
